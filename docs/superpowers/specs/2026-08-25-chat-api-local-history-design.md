# BuzzBot Chat API and Local History Design

**Date:** 2026-08-25  
**Status:** Approved for implementation

## Goal

Replace the frontend shell's mock conversation and mock history with the real
BuzzBot `POST /v2/chat` API and browser-local conversation persistence. Keep the
existing UI direction, do not implement authentication, and preserve stable
thread identifiers so local conversations can be imported into an account after
authentication is added later.

## Scope

This iteration delivers:

- real non-streaming calls to the existing FastAPI `/v2/chat` endpoint;
- continuation of a selected conversation using its `thread_id` and recent
  message history;
- functional New chat, history selection, local history search, reload
  restoration, and retry after request failure;
- rendering of real answers, citations, confidence, freshness, and notes;
- configurable backend CORS origins for local and future deployed frontends;
- deterministic frontend and backend tests with no paid live model call.

This iteration does not deliver authentication, cross-device sync, server-side
conversation storage, streaming, chat rename/delete controls, personalization,
or analytics. Settings remains an explicitly disabled future location.

## Chosen Architecture

The browser calls FastAPI directly. A small API module owns HTTP serialization
and response validation. A small storage module owns the versioned localStorage
format. `BuzzBotApp` remains the single UI state owner and composes those two
modules; no global state library, proxy route, or repository class hierarchy is
introduced.

```text
Sidebar / ChatWorkspace
        │
        ├── chat-storage.ts
        │     └── localStorage: buzzbot.chat.v1
        │
        └── chat-api.ts
              └── POST ${NEXT_PUBLIC_BUZZBOT_API_URL}/v2/chat
                    query
                    thread_id
                    history (last 20 completed turns)
```

The default API origin is `http://localhost:8000`. Deployment overrides it with
`NEXT_PUBLIC_BUZZBOT_API_URL`; no API key or secret is present in browser code.

## Backend Contract

The existing backend request is used unchanged:

```json
{
  "query": "Is CS 6601 offered in Fall 2026?",
  "thread_id": "a UUID generated by the browser",
  "history": [
    { "role": "user", "content": "previous question" },
    { "role": "assistant", "content": "previous answer" }
  ]
}
```

The frontend consumes `thread_id`, `answer`, `citations`, `confidence`,
`freshness`, and `notes`. `debug` may remain in the HTTP response but is not
shown in the student-facing interface.

The API URL is normalized by removing a trailing slash before appending
`/v2/chat`. The API module accepts an `AbortSignal`, rejects malformed success
payloads, and maps HTTP/network failures to a short user-safe message. For a
429 response, the backend's safe `detail.message` and optional retry interval
may be shown. Raw stack traces and response bodies are never rendered.

## Local Conversation Model

The stored document has an explicit schema version:

```ts
type StoredChatState = {
  version: 1;
  activeConversationId: string | null;
  conversations: StoredConversation[];
};

type StoredConversation = {
  id: string; // also sent as thread_id
  title: string; // first user question, compacted for the sidebar
  createdAt: string;
  updatedAt: string;
  messages: StoredMessage[];
};

type StoredMessage = {
  id: string;
  role: "user" | "assistant";
  content: string;
  createdAt: string;
  status: "complete" | "failed";
  citations?: ChatCitation[];
  confidence?: number;
  freshness?: FreshnessInfo;
  notes?: string[];
};
```

Storage parsing is fail-safe. Missing storage starts empty; invalid JSON,
unknown versions, or invalid top-level shapes are ignored instead of crashing
the page. The implementation keeps at most 50 conversations and 40 messages
per conversation to avoid uncontrolled localStorage growth. Only completed
turns are sent to the backend, and only the latest 20 turns are included.

An empty New chat remains in memory and is persisted only after its first
question, avoiding empty history entries. A failed request keeps the user's
message with `status: "failed"` so it can be retried, but that failed turn is
excluded from future context until retry succeeds.

## Conversation Behavior

### New chat

New chat aborts an in-flight request, clears the active draft, and returns to
the empty workspace. It does not erase existing conversations.

### Continue chat

Selecting a history entry loads its stored messages. The next submission uses
the same conversation ID as `thread_id` and sends the latest 20 completed prior
turns. The newly submitted question is not duplicated in `history`; it is sent
only as `query`.

### Search

Search chats toggles a native sidebar search input and filters locally by
conversation title and message content. An empty search shows all history.
Search does not call the backend.

### Loading and retry

Only one request can be active. While pending, the composer is disabled and a
polite Thinking status is shown. New chat or selecting another conversation
aborts the old request. A failed request displays an inline error and Retry
control. Retrying reuses the failed question and the same `thread_id`.

## Answer Rendering

The hard-coded `MOCK_ANSWER` schedule table and mock sources are removed from
the runtime path. The real API answer is rendered as plain text paragraphs.
This preserves the backend's conversational synthesis for both policy and SQL
schedule results rather than presenting a raw fetch response.

Each citation shows its title, official URL, exact quote, and optional fetched
date/page. Links open in a new tab only when the URL uses `http` or `https`.
Confidence, freshness, and notes appear as quiet supporting metadata. React's
normal text escaping remains the rendering boundary; raw HTML is never used.

The three likely questions remain static because they are navigation prompts,
not simulated backend data.

## Sidebar History

The hard-coded history fixture is removed from the runtime path. Stored
conversations are sorted by `updatedAt` descending and grouped into Today,
Previous 7 days, and Older. Selecting an entry sets it active and closes the
mobile drawer. The active conversation receives the existing selected style.

Search chats becomes enabled. Settings remains disabled with an accessible
explanation because authentication and personalization are explicitly outside
this iteration.

## Future Auth Import

No login code or server history endpoint is added now. Stable conversation and
message UUIDs, timestamps, and schema version make a later account import
possible. After login, the product should ask before importing this browser's
anonymous conversations, then deduplicate by conversation ID and resolve
updates by `updatedAt`. Automatic import is intentionally avoided because it
could attach another person's conversations on a shared computer to the wrong
account.

## Backend CORS

FastAPI's allowed origins become environment-configurable through a
comma-separated setting. Local defaults cover ports 3000 and 3100 on localhost
and 127.0.0.1. The production frontend origin must be explicitly configured;
wildcard origins are not allowed, especially while credentials remain enabled.

## Testing

Frontend tests cover:

- API request serialization, safe response parsing, 429 mapping, and abort;
- storage load/save, invalid data recovery, limits, and history projection;
- new chat, real history selection, local search, reload restoration, request
  loading, success, failure, retry, and continued-chat history handoff;
- citation URL safety and real response rendering;
- Playwright API interception proving the UI sends the expected `/v2/chat`
  payload and restores history after reload.

Backend tests cover configured CORS origin parsing and middleware behavior.
No test calls OpenAI, LangSmith, or a live BuzzBot endpoint.

## Acceptance Criteria

- A user can ask a question and see the real `/v2/chat` response.
- A second question in the same conversation sends the same `thread_id` and
  prior completed turns.
- Reloading preserves and restores conversations in the same browser.
- New chat, history selection, and search are functional.
- Failed requests are understandable and retryable without corrupting history.
- No mock answer or mock history is used in the runtime path.
- No authentication or secret is added to the frontend.
- Existing frontend and backend deterministic tests do not regress.
